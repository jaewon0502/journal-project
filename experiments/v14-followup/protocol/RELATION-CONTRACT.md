# New v14 follow-up relation contract — version 1

This is a newly implemented, deterministic follow-up gate inspired by the archived v13 gate and the public v14 report's P2/P5 relation problem. It is **not recovered v14 code, a replay of the original v14 run, or evidence of improved real-article accuracy**. The original v14 runtime, proposal JSON, and exact review records were unavailable for this implementation. The archived v13 code and historical counts remain untouched.

The contract below and the validation in `../code/gate.py` define the new input format. Only Python's standard library is required. The tests author synthetic text, judgments and audits; no fixture is a human assessment or a new semantic evaluation of the real v14 article.

## Run and API

From the repository root:

```sh
python3 experiments/v14-followup/code/gate.py prepare bundle.json prepared.json
python3 experiments/v14-followup/code/gate.py evaluate bundle.json review1.json review2.json provisional.json
python3 experiments/v14-followup/code/gate.py evaluate bundle.json review1.json review2.json audited.json --audit audit.json
python3 -m unittest discover -s experiments/v14-followup/code -p 'test_*.py' -v
```

The Python API is `prepare(bundle_raw: bytes)` and `evaluate(bundle_raw: bytes, review_raws: list[bytes], audit_raw: bytes | None = None)`. No network or model calls occur. No file is published. CLI validation/audit rejection exits with code 2; a valid provisional or held result exits with 0. Exit code 0 never means permission to publish: consumers must require both `status == "approved"` and `publication_allowed == true` for the exact `candidate_text`/`candidate_sha256` returned. `semantic_certification` is always false.

`prepare` returns the parsed bundle, binding, and `full_proposed_candidate`, which applies every proposal for review preview, including optional proposals. This preview is not the selected candidate and is not approved. The gate computes the selected candidate itself from exact original spans; callers cannot supply arbitrary candidate text for publication. A malformed bundle causes Python `prepare` to raise `Invalid`; the CLI records `validation_failed`. Python `evaluate` returns a failure record for invalid input.

## Exact data shapes

All objects require exactly the listed fields. Unknown and missing fields, duplicate JSON object keys, invalid JSON constants, empty IDs, duplicate proposal/document IDs, and missing/unknown/duplicate assessed IDs fail validation. Strings are UTF-8; SHA-256 means lowercase hexadecimal SHA-256. Arrays marked as ID arrays contain unique IDs. JSON examples and a complete fixture are in `../code/test_gate.py`.

**Bundle**

```text
{
  bundle_id: nonempty string,
  original_article: nonempty string,
  evidence_documents: [{id: nonempty string, text: nonempty string}],
  proposed_patches: [{
    id: nonempty string,
    before: nonempty exact unique substring of original_article,
    after: string (empty permitted for a justified deletion),
    kind: "necessary_correction" | "optional_enrichment"
  }]
}
```

Evidence IDs `original` and `candidate` are reserved. Spans use Python character offsets in the exact original text; no whitespace or Unicode normalization occurs. Every original span must occur exactly once, including overlapping occurrences, and all proposed spans must be disjoint. A patch whose before and after are identical is invalid. Empty `proposed_patches` is valid. It does not prove that the original has no semantic errors or that the evidence is complete.

**Input binding**, generated by `prepare` and copied exactly into each review:

```text
{
  bundle_id,
  input_sha256,     # exact input JSON file bytes, including whitespace
  original_sha256,  # original_article encoded as UTF-8
  evidence_sha256,  # canonical evidence_documents
  patches_sha256    # canonical proposed_patches
}
```

Canonical JSON uses `ensure_ascii=False`, `sort_keys=True`, compact `(',', ':')` separators, `allow_nan=False`, then UTF-8 encoding. Hashes bind supplied material, not its truth or provenance.

**Each of exactly two review records**

```text
{
  reviewer_id: nonempty string,
  binding: exact input binding,
  complete: boolean,
  read_complete: boolean,
  patch_assessments: [{
    patch_id: proposal ID,
    kind: "necessary_correction" | "optional_enrichment",
    necessity: "yes" | "no" | "unknown",
    evidence_support: "yes" | "no" | "unknown",
    preserves_other_meaning: "yes" | "no" | "unknown",
    context_safe: "yes" | "no" | "unknown",
    atomic: "yes" | "no" | "unknown",
    related_context: [proposal ID],
    required_dependencies: [proposal ID],
    relation_status: "complete" | "unknown",
    anchors: [{document_id: original or evidence ID, quote: exact nonempty substring}],
    reason: nonempty string
  }]
}
```

The two reviewer IDs must differ. Both completion flags must be true. Assessments cover every proposal exactly once, even held or optional proposals. Each assessment needs at least one exact known anchor. An exact anchor validates citation location only; it does not prove the conclusion follows from the quote.

## Relation and atomic-edit rules

`related_context` means relevant context which does **not** need to be edited for this patch to be safe. `required_dependencies` means every listed patch must be selected for this patch to be safe. Relations belong to independent reviewers' judgments, not a writer's ambiguous `related_patches` field. Unknown references, repeated IDs, self references, and an ID in both arrays are invalid. The legacy `related_patches` field is rejected instead of silently migrated.

Both reviewers must agree on the **required_dependencies** set; order is irrelevant. A required-vs-related disagreement is unresolved and holds the affected patch. When both declare complete relation analysis and agree on required dependencies, differing non-required context annotations are recorded in `relation_notes` for the final auditor, without holding an otherwise passing patch. Merely relevant context must not become a hidden required dependency. Unknown relations still hold the affected patch. This policy and its regression tests do not prove that reviewers can classify every semantic dependency correctly.

`relation_status = unknown` holds only that patch and patches which require it. It does not hold unrelated proposals. A structurally invalid record (for example an unknown proposal ID) fails the whole evaluation, because its intended target cannot be safely inferred.

Only `necessary_correction` proposals can be selected. The proposal kind and both review kinds must agree, all four axes must be `yes`, and both `atomic` judgments must be `yes`. Atomic means one independently justifiable correction, without a bundled optional explanation, background addition, or stylistic enrichment. Split a necessary correction and optional enrichment before review; the gate does not automatically rewrite or split text. Two reviewers saying yes does not make optional enrichment eligible. Semantic atomicity is assessed by reviewers; the code cannot infer it from prose.

After local selection, required dependencies are enforced to a fixed point. A mandatory cycle may be selected only when every member independently passes; if one is held, the connected dependants are held. Context-only links do not propagate holds. Even a complete passing cycle remains provisional until its exact combined candidate receives a final audit.

## Final audit and status

Two initial reviews authorize a provisional selection only. Evaluation returns `awaiting_audit` if at least one patch is selected and no audit is supplied. Its `audit_binding` includes the input binding, `reviews_sha256` of the **exact two raw review files in CLI order**, `selected_ids` in proposal order, and `candidate_sha256` of the exact selected candidate. `selection_sha256` hashes canonical JSON of these fields before the selection hash itself is added.

The subsequent separate audit must bind that exact selection:

```text
{
  auditor_id: nonempty string different from both initial reviewer IDs,
  binding: exact audit_binding,
  complete: boolean,
  read_complete: boolean,
  full_candidate_assessed: boolean,
  assessed_patch_ids: [every selected ID exactly once],
  unassessed_spans: [{document_id: "candidate", quote: exact nonempty substring}],
  verdict: "approve" | "hold" | "unknown",
  anchors: [{document_id: original, candidate or evidence ID, quote: exact nonempty substring}],
  reason: nonempty string
}
```

Approval requires all three booleans true, every selected patch assessed, `unassessed_spans` empty, nonempty valid anchors when any patch was selected, and verdict `approve`. A stale or malformed audit, mismatched candidate hash, changed input/review bytes, omitted patch assessment, any unassessed candidate span, or `hold`/`unknown` verdict sets `audit_rejected` and leaves publication disallowed. A valid approved audit changes a nonempty provisional selection to `approved`; the entire original article is still not truth-certified. Audit data does not itself publish anything.

If there are no proposals, valid empty reviews produce `no_op`; if proposals exist but none can be selected, status is `held`. Even an affirmative audit cannot turn an unchanged candidate into an approved correction or semantic certification. Review/audit identities, independence, full-reading declarations and timestamps are not authenticated by this local gate. Hashes prevent unnoticed reuse against different supplied inputs; they are not signatures and cannot detect coordinated rewriting of all records. A later exact-selection binding is necessary but does not prove when or how an auditor performed the work.

## Reviewer and final-auditor instructions

Give each initial reviewer the full original, all evidence documents, all exact proposed patches and the full proposal preview. Keep the two reviews independent; do not reveal the other review, anticipated acceptance count, author rationale or desired outcome. Read the original before the candidate. Evaluate correction necessity separately from whether added information is useful. Inspect both changed text and all relevant unchanged surrounding context; unknown dependencies must remain unknown.

For `context_safe = yes`, the change must be safe when its declared required dependencies are applied, without assuming that context-only patches also pass. Check the case where a related patch stays unchanged. For `atomic = no/unknown`, explain the mixed or uncertain portion rather than approving a necessary core plus optional tail. Use exact source/original anchors and explain each no, unknown, kind decision or relation. Missing source support alone is not evidence that an unchanged original claim is false.

The later auditor receives the exact selected full candidate and hash binding, original, all supplied evidence, selected edits and the limits of the task. Assess the full candidate, including unchanged text around edits and long-distance interactions. A per-patch check alone is insufficient. Record unassessed candidate spans; use `unknown`/`hold` when assessment is incomplete or context safety is unresolved. Separate inherited original gaps from newly introduced errors and do not treat preserved original text as certified truth. Do not invent a human judgment, independently sourced accuracy result or model-family independence claim.

## Verification scope

The test suite covers the disclosed P5/P2 relation structure using invented text, mandatory chains and cycles, reviewer disagreement, relation uncertainty, optional enrichment, atomicity, exact spans and overlap, evidence anchors, IDs, input/review/audit hash binding, unassessed candidate text, no-op semantics, and the CLI. These are deterministic mechanical regression tests. They do not measure real-article correction quality, whether actual reviewers reliably recognize mixed edits, model accuracy, or human agreement.
