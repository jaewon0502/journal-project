# Fixed independent reviewer instructions

Read the entire supplied wrapper: source documents, scope note, full original article, all fixed questions, every proposed patch and the full simultaneous candidate. Do not infer truth from another reviewer, anticipated gate behavior, author intent, or majority agreement. Complete one independent pass; do not see other review judgments. Candidate application errors must be reported, not repaired. No new replacement text is requested.

Return ONLY a JSON object conforming to REVIEW_SCHEMA.json. Copy bundle_id and the four SHA256 values exactly from wrapper.binding; these bind the exact input file and canonical source/proposal arrays plus original UTF-8 bytes. Set complete and read_complete true only if the entire task was completed. If reading is incomplete, return complete/read_complete false with your available report; the gate will hold on schema validation. Every proposed patch must have one assessment, including unsafe or uncertain proposals; no additional or duplicate IDs.

Five fields use only yes/no/unknown:
- warranted: the change is a necessary factual or meaning correction, not merely preferred wording.
- evidence_support: supplied source evidence supports this exact change, allowing explicitly disclosed limits of source scope. Missing evidence alone is not refutation.
- preserves_untargeted_meaning: the change preserves meaning outside its justified correction, including criticism, responsibility, attribution, actor, strength, conditions, negation, numbers, time, comparisons and causality.
- context_safe: the patch is safe in the article when all explicitly listed required dependencies are also applied. Check original, candidate and surrounding sentences/paragraphs for changed relations; approval conditional on another change requires that patch ID in dependencies. Assess the full candidate for interactions; do not equate isolated sentence correctness with contextual safety.
- application_valid: before is an exact unique span of original_article, after faithfully expresses the assessed change, and application creates no overlapping/conflicting span problem.

List all required patch IDs in dependencies. Set dependency_status complete only if dependency analysis is complete. Possible unidentified dependencies require unknown and cannot be assumed safe. Cycles are allowed only when all members are approved together; the combined candidate still needs a later independent final audit. Explain uncertain dependencies and contextual interactions in reason.

Each patch reason must explain its judgments, including each no/unknown; supply at least one exact source or original anchor as {document_id,quote}. document_id is a source paragraph ID or "original". Quote must be an exact substring of that document. Use multiple anchors whenever comparisons require them. Provide qualitative confidence low/medium/high; confidence never overrides uncertainty.

List original/background issues separately, with status resolved/unresolved, material yes/no/unknown, all affected patch IDs, unrelated_to_edits yes/no/unknown, anchors and reason. Unresolved empty affects_patch_ids is considered unrelated ONLY when unrelated_to_edits=yes and reason affirmatively explains why the issue does not touch an edit, its surrounding relation, or a dependency. Never use an empty mapping to hide unlocalized risk. Unknown relation requires unknown; mapped issues must not be simultaneously called unrelated. Unrelated original evidence gaps remain original limitations, not newly introduced harm.

Set global_material_risk yes for unresolved new or edit-related material candidate risk not safely localized to patch IDs, unknown if global safety or localization remains unresolved, and no only when no such unresolved global risk is identified. Explain in global_risk_reason and cite exact global_risk_anchors when risk is yes/unknown. An unchanged unsupported original claim alone is a background issue, not global new/edit-related risk. If an edit depends on an original evidence gap, map that gap to the affected patch IDs and assess materiality; do not classify it as unrelated. Any affirmative unrelated classification must cite anchors and explain its separation from edits and dependencies. These definitions are frozen before review execution; do not downgrade risks to enable release. Localized held patch problems belong in patch fields or mapped background issues; do not label all local problems global by default.

Record pure style/tone/preference differences in preference_differences with an affirmative explanation why they do not alter meaning. Sentiment, negativity, criticism, disliked tone, or stylistic preference alone must never veto a supported correction or justify removal of supported meaning. Semantically consequential tone/strength changes still require assessment as meaning changes.

Overall_reason records important residual limitations and findings. No scores, author expectation guesses, gate names, or release recommendation. These reviews are not final safety audits.
