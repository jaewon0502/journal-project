# v17 common writer instruction — proposed, pre-development

Read the full supplied original O, candidate C, source packet S, reader question Q and source/version metadata. Use only this input: local tools may read the explicitly assigned input files and save the actual answer to the assigned output file; external tools, search, retrieval, reads of other files, other candidates and prior trials are forbidden. Return one JSON object conforming to the supplied common schema. Apply the accompanying method instruction. The original is not factual gold. This is a minimal necessary correction task, not a compression task; preserve meaning at its needed length. There is no arbitrary article-length or output-compression target. Do not rewrite the full article or add stylistic improvements.

Read the full available headline, subtitle, body and captions. Distinguish new edit losses, inherited original problems and source-only details. Identify errors or materially missing conditions using short exact candidate/original/source anchors. A source document's existence does not establish its applicability or version. A proposal, draft, summary, press release, agreement or adopted text is not automatically final published law or evidence of what was publicly available on an earlier date. State unresolved version/time/coverage limits. Preserve attributed criticism, opposing views, uncertainty and claim strength; evidence that someone said something is not proof their prediction or allegation is true.

Operational judgments (yes/no/unknown):
- factual_error: a specific candidate proposition is directly contradicted by S with matching subject, time, unit, scope and attribution. Absence of evidence is not a contradiction.
- original_meaning_loss: meaning actually present in O is absent or changed in C. Source-only details are not original losses. Explain justified corrections of original errors separately.
- conclusion_changing_omission: an omitted condition changes the supported answer to Q or the stated scope, responsibility, attribution or claim strength. Give the missing condition and concrete before/after proposition grounded in the packet. If full context restores the restriction, no; if reasonable interpretations differ, unknown. Do not invent an external counterexample.
- required_answer_missing: C supplies no answer to an identified atomic part of Q anywhere in its full context. An explicit but incorrect answer is not a missing answer.
- answer_present_but_incorrect: C explicitly answers that same atomic question incorrectly according to S. For that atomic question this and required_answer_missing cannot both be yes. Separate atomic questions into separate findings if needed.
- optional_clarification: a supported detail could improve explanation but the answer, scope, attribution and force are already intact. For the same detail this cannot coexist with necessity=yes or conclusion_changing_omission=yes. Utility or importance to a reader is not by itself factual necessity. opinion/value disagreements alone do not authorize factual patches.

Overlap is allowed across factual_error, original_meaning_loss and conclusion_changing_omission when separately justified. Example: S/O says an entitlement is for residents aged 16+, C says everyone qualifies. This may be a factual error and a condition omission and original loss; the eligibility answer is present but incorrect, not absent. If C says nothing about the eligibility question, required_answer_missing may be yes and answer_present_but_incorrect no. If Q asks only the commencement date, an unrelated optional procedural detail is not a required missing answer. These are semantic examples, not evaluation items.

For each finding record only relevant evidence relations actually used: a supporting or contradicting clause and, if used, its directly linked definition, exception, scope or timing clause. Both methods use the same evidence_relations field. Empty is permitted when no source relation is relied on; do not invent a relation or fill a table for every article sentence. Record why the relation affects the proposition or why a superficially related detail does not. Exact short quotes plus packet document/section locators are sufficient. These records are witnesses, not hidden chain-of-thought.

Patch only an established necessary correction that S or faithfully preserved attribution supports, where necessity, evidence_support, preserves_other_meaning and context_safe are all yes. Return an exact unique C span before and its minimal replacement after; preserve all unaffected meaning. If restoring O would contradict S, prohibit that restoration, but allow a directly supported alternative correction with all four gates yes. Do not hold a supported alternative merely because O was wrong. Avoid overlapping/duplicated patches; express any required co-application through depends_on. An unmet or uncertain necessary dependency holds only the affected set.

Use no_change for no established necessary correction or only optional clarification. Use hold for an identified issue whose necessary correction, evidence or safety is unresolved; a rejected optional edit is not a hold. A recognized error with an unsafe correction can be detected yet held. List local reasons H-E evidence, H-N necessity, H-S safety, H-D dependency, H-X technical contract. Keep unrelated coverage H-C separate; explain why it is unrelated. Unknown influence on a patch requires appropriate local hold, not automatic approval. Do not hold every local edit merely because the packet cannot certify every article claim.

Before returning, consider the entire C with all proposed patches applied, including their interactions. Record selected_candidate_delta_safety safe/unsafe/unknown. This self-check does not replace the separate full actual-applied-candidate audit. preservation_decision is repair if at least one safe patch is proposed (also list other held findings), hold if none is proposed and an identified necessary issue remains unresolved, otherwise no_change. overall_readiness concerns coverage and remaining errors in the supplied task only: ready/not_ready/unknown; it is never publication authorization or a legal certification. Use needed output length. Findings may be empty; do not manufacture issues or extra detail to populate fields.

Serialization rule: source_refs must contain ONLY exact values from the input sources[].id (for example S1), never a combined ID plus section description. Put section descriptions only in the witness locator field. supporting_clause.document_id and linked_clause.document_id must likewise be exact source IDs.
